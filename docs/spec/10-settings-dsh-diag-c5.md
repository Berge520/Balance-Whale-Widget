  - **⚠️ C5 端口 pid 踩坑（v1.6.2 修复）**：`portState.pid` 原写成 `num(snap.externalPid) || (snap.portOther ? num(snap.pid) : 0) || num(snap.pid)`：末尾 `num(snap.pid)` 是**本插件 spawn 的子进程 pid，与端口归属无关**。当 dsh 正是本插件启动时（`externalPid` / `portOther` 都为空，`dsh.js` 靠 `probe.pid !== state.pid` 区分「外部 dsh」），界面会把插件的 `cmd.exe` 包装进程 pid 当成「占用 3080 的进程」显示，而真正监听 3080 的是 `node.exe`。**pid 宁可为 0（走「无法判定」），不能给错的值。** 同时补 `portState.selfOwned`（取 `snap.ready`，即「3080 已开始监听」，不是 `running`「只是有子进程」）：端口在监听、非外部、无人占用 ⇒ 就是本插件这份 dsh 在服务，C5 据此报「由本插件的 dsh 监听」而非「无法判定」。该分支必须排在「拿不到进程名」之前。`selfOwned` 不覆盖 `occupiedByOther`（别人占用仍是 `error`）。
  - **⚠⚠ C5 判据把它人的 node 进程认成 dsh（v1.6.2 修复，第二次「测试与实现共享同一个错误假设」）**：判据原为 `isDshName(name)`，只看进程名 `/^(node|dsh)(\.exe)?$/i`：**任何 Node 程序都叫 `node.exe`**，等于没判。实测：起一个裸 `node -e "net.createServer().listen(3080)"` 占住 3080，诊断报 `[!] 已有外部 dsh`（warning）而非 `[✗] 被非 dsh 占用`（error），**漏报真占用**，用户按「可改为接管这个实例」去点必然失败。
    - **判据改为看命令行，三态**：新增纯函数 `looksLikeDsh(cmdline)` 返回 `true`（含 dsh 特征）/ `false`（能证明不是）/ `null`（拿不到命令行）。特征正则 `DSH_CMDLINE_RE` 认 `@deepseek-ai/dsh`、`dsh/lib/bin.js`、`dsh.cmd|exe|js`、`@deepseek-ai/dsh-*`（真 dsh 命令行含 `@deepseek-ai\dsh\lib\bin.js`；`npm-cli.js run dev` / `vite.js` 与探针都不含特征）。配套 `processCmdline(pid, cb)`：Windows 优先 `wmic process ... get commandline /value`（**不能用 `tasklist`，只给进程名，本 bug 根因就是「只有名字」**），wmic 被移除时退回 `powershell Get-CimInstance Win32_Process`，都拿不到返回 `''`；POSIX 走 `ps -p <pid> -o args=`。`probePort` 内名字与命令行**并行**取，都回来才算完成；`snapshot()` 暴露 `portDsh` / `portCmdlineKnown`。
    - **C5 判据链（改后顺序）**：探测未执行 / `failed` → `[!]`；`pid` 为 0 → `[✓]` 空闲；`occupiedByOther` → `[✗]`；`externalPid` → `[!]` 外部 dsh；**`portDsh === false` → `[✗]`（新增分支）**；`portDsh === true` → `[✓]` 本插件的 dsh；其余 → `[!]`「无法判定」。
    - **`dsh.js` 的两处同步收紧**：`externalPid()` 加 `looksLikeDsh(probe.cmdline) === true` 条件（名字像不算数，宁可返回 0 报「无法确认」，不能把别的程序说成 dsh 骗用户「接管」）；`portOccupiedByOther()` 对「名字像但命令行证明不是」的情况也返回进程名（此前直接放行 = 漏报）。
    - **顺带收掉 `ps.name` 与 `ps.selfOwned` 两条早返回**：补测时发现 `portDsh: null` + `name: 'node'` 仍落进 `if (ps.name)` 报 `[✓]`，**那还是拿名字当证据，只换了方向**；`name: 'nginx'` + 拿不到命令行时同样报 `[✓]`。**「是本插件的 dsh」的唯一通路是 `portDsh === true`**，`selfOwned` 在新模型下冗余（本插件的 dsh 必然命令行含特征）。修 `[✓]` 侧假通过比修 `[✗]` 侧更重要：前者是「诊断说没事、其实起不来」。
    - **⚠ 测试侧同样的错**：既有用例 `{ pid: 22, externalPid: 22, name: 'node' }` 与实现同一个假设（「pid 存在 + 名字是 node.exe = dsh」），**四关全绿也拦不住这个 bug**。上一次同类事故是 C2/C3 双双少写一层 `profiles/<n>`。教训：判据凡有「靠名字/靠路径就能认出来」的地方，都拿真实样本（真 dsh、别的 node 进程、探针各一条）钉死。现补 4 条：`looksLikeDsh` 三态、C5 `portDsh:false → [✗]`、`portDsh:null → [!]`（含 `node` / `nginx` 两种名字）、以及「同名不同 `portDsh` 结论必须从 `[✓]` 变 `[!]`」的反向钉子（防止有人把名字判据改回来）。
  - **⚠⚠ C5 认不出「自己人」：Windows 的 `cmd.exe` 中间层（v1.6.2 修复，第三次「测试与实现共享同一个错误假设」）**：`dsh.js` 启动走 `spawn(..., { shell: true })`，Windows 下插入一层 `cmd /c`，**插件拿到的是 `cmd.exe` 的 pid，真正监听 3080 的是子进程 `node.exe`**。于是 `probe.pid !== state.pid` 恒成立，自己启的 dsh 被算成「外部 dsh」，界面显示「外部 dsh · 请到别的终端查看」并禁用启动按钮。**判据改为父链上溯**：新增 `processParent(pid, cb)` 取 `ParentProcessId`（Windows 走 `wmic process ... get parentprocessid /value`，wmic 被移除时退回 `Get-CimInstance Win32_Process`；POSIX 走 `ps -p <pid> -o ppid=`）与纯函数 `isDescendantOf(pid, self, parents)`（邻接表 + 沿父链最多上溯 8 层，**带访问集合防环**）。`isSelfOwnedPort(pid, cb)` 先比同 pid，再上溯判断是否为本插件后代。实测链：`插件 → cmd.exe → node.exe（监听 3080）`。
    - **状态卡 pid 与诊断 pid 必然不同**：状态卡认 `state.pid`（spawn 句柄 = `cmd.exe`），诊断报真正监听的 `node.exe`。这是正常现象，**不是 bug**，写文档与提示文案不许把它当成「不一致」。
    - **`probe.busy` 不能当业务结论**：`external` 一度写成 `!!externalPid() || !!probe.busy`，但 `probe.busy` 是异步探测的**工程状态**，`watchReady` 每 1.2s 探一次，插件自己启动 dsh 后长期为 true → 界面显示「外部 dsh · pid 0」。现改为 `external: !!externalPid()`（`externalPid()` 读已算好的 probe 结果，未算好保守返回 0），是否 busy 交给 `extBusy` 表达。
  - **⚠⚠ C5 探测蹭上「陈旧轮次」：`waiters` 排队复用（v1.6.2 修复）**：`probePort` 原有的排队复用（`if (probe.busy) probe.waiters.push(cb)`）本为合并并发调用，但**诊断点「强制重跑」时极可能撞上 `watchReady` 正在跑的那一轮**：那一轮的 `netstat` 是在 dsh 还没 bind 3080 时跑的空结果，于是诊断报「3080 空闲」，而状态卡同时显示「运行中」。实测 `netstat -ano` 有进程在 `127.0.0.1:3080` 上 LISTENING。
    - **修法：轮次号 `gen` + `force`**。`probe` 加 `gen`（单调递增轮次号）；`probePort(cb, force)` 在 `force=true` 时**即使有探测在跑也另起一轮**，两轮并存；纯函数 `__isStale(myGen, latestGen)` 判定某轮已被取代，**只让最新一轮写 `probe`**（`probe.pid` / `name` / `cmdline` / `selfOwned` 的写入前逐个判 stale）。`detectPort` 一律传 `force=true`。
    - **`flushProbe(cb, gen)` 的守卫要给对**：**最新的轮次**才清空 `waiters` 并逐个回调；旧轮不许放行 waiters，**但必须回调它自己的 `cb`**：第一版写成「旧轮直接 return」，把旧轮调用方的回调吞掉，`detectPort` 只能等 8s 超时兜底（实测只有 force 轮回调了）。给旧值也比永不回调好。
  - **⚠⚠ C5 的 `pid` 字段一字段两义：把「有没有人占」与「占的是不是外人」混为一谈（v1.6.2 修复）**：`detectPort` 原写成 `pid: num(snap.externalPid) || (snap.portOther ? num(snap.pid) : 0)`：`pid` 被 C5 当作「端口上有没有人」（`if (!ps.pid)` → 报「3080 空闲」），实际填的却是「**外部占用者**是谁」。**本插件自己启的 dsh 两个来源都为空**（`externalPid=0`、`portOther=''`，`externalPid()` 只认外部 dsh）→ `pid` 置 0 → C5 判「3080 空闲（无进程监听）」，而状态卡同时显示「运行中」，自相矛盾。
    - **修法：拆成两个字段**。`snapshot()` 新增 **`portPid`**（真正监听端口的进程，本插件启的 / 外部的 / 别的程序都算）与 **`portName`**（同口径的进程名），未探测完时给 0 / `''`；`detectPort` 改用 `num(snap.portPid) || num(snap.externalPid) || (snap.portOther ? num(snap.pid) : 0)`，`name` 也先取 `portName`。**「端口上有没有人」与「占的人是不是外人」是两件事，必须两个字段**。
    - **`probePort` 的两轮并存反过来要求 `portPid` 也做 stale 保护**：`portPid` 取 `probe.busy ? 0 : probe.pid`。
    - **`portDsh === true` 分支的 summary 必须带 pid**：用户对照状态卡（`cmd.exe`）与任务管理器（`node.exe`）排查时，**只有这个 pid 是「端口上那个人」**。这条写测试时才发现实现漏了（断言 pid 失败），「测试与实现共享错误假设」的又一次变体：这次测试反而是对的。
    - **C5 判据链（补全后，含 `portDsh` 与 `selfOwned`）**：`!ps` / `ps.failed` → `[!]`；`!ps.pid` → `[✓]` 空闲（pid 取自 `portPid`）；`occupiedByOther` → `[✗]`；`externalPid` → `[!]` 外部 dsh；`portDsh === false` → `[✗]`；`portDsh === true` → `[✓]` 由本插件的 dsh 监听（带 pid）；`selfOwned` → `[✓]`；其余 → `[!]` 无法判定。三态实测：插件自启 → `[✓] 由本插件的 dsh 监听（node.exe）`；外部 dsh 占着 → `[!] 已有外部 dsh 在运行`；真空闲 → `[✓] 3080 空闲`；裸 node 探针占着 → `[✗]`。

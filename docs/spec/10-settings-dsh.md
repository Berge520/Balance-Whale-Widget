- **「DeepSeek Harness（dsh）」卡片**（「开发者」Tab 独占一组）：注册源 / 版本（默认「自动」＝安装 / 更新时取 latest，可固定版本；先「查询可用版本」再选）/ Node.js 目录（「选择目录」或「改为自动探测」）/ 启动带 `--no-open` / Web UI 端口（默认 `DSH_PORT_DEFAULT` = 3080，可改；**改端口只写配置，运行中的进程仍在旧端口，须点「重启」才切过去**；状态行写明「现监听 Y，点重启生效」）/ 更新前重新下载 / uTools 退出后是否保留 dsh；只读展示插件目录 / 全局安装（按平台标注 UAC / 提权）/ 实际使用（含 `source`）/ 状态与最近命令 / 页面地址；「删除插件目录里的 dsh」「清理 npx 旧缓存」「清理残留写锁」三个维护按钮均点两次执行。
  - **卡内分两折叠**：**「诊断信息（版本 / 命令 / 地址 / 日志）」**（`dshFolds.versions`）含「实际使用 / 全局安装 / 插件目录 / npm latest」四行、「最近命令」「页面地址」两行，以及「查询可用版本 / 复制全局路径 / 复制插件路径 / 复制地址 / 查看日志 / 清空日志 / 复制日志」按钮与日志框；**「高级选项」**含版本 / 注册源 / Node.js 目录 / **Web UI 端口**四个设置项 + 三个行为开关。**只读诊断与可写配置分离**：卡内常显区只留状态行 + 启停按钮 + 外部进程/端口提示 + 错误与成功提示，「刷新状态」等只读动作不进「高级选项」。
  - **展开诊断折叠即自动查版本**（`dshToggleVersions()`）：尚无 `versions.latest` 时自动调 `dshQueryVersions()`，「npm latest」**不是「版本最大值」**，而是「点『更新』会装到的版本」（latest tag 指向的版本）。
  - **版本错位提示**（`dshVerMismatch`）：`dsh.hasUpdate` 为假但**实际使用版本 ≠ npm latest** 时，按钮行上方显示「当前 X 与 npm latest（Y）不同，点『更新』会替换为 Y」：更新会**替换**成 latest，可能比在用的旧。`hasUpdate` 为真时不显示（状态行 `dshLatestTip` 已覆盖）。**`hasUpdate` 只比 npm latest，「谁更新」按发布时间判**：曾用 `isNewer(targetVersion(), act.version)`，而 `targetVersion()` 优先返回手选固定版本（实装与下拉都选 alpha.2 即判成无新版，而 latest 是 rc.2）；用户选哪版只决定「更新装哪版」，不改写「npm 上有没有新版」，故只比 `latest`、改用 `newerByTime`（按 `times`，缺 `times` 才退回 `isNewer`）。「有没有新版」与「点更新会装成哪版」是两件事，后者归 `dshVerMismatch`，两条提示不重叠。
  - **「版本说明」折叠行（`dshFolds.notes`）**：不只取上游 `releases/latest`（只讲相对上一版改了什么），改为按「实装版本 → 目标版本」**聚合整个区间**的 release notes；实装即最新时区间为空。**入口不依赖取数结果**（`dshNotesRow`）：版本列表已查到就给折叠行，点开才取 —— 反过来「有结果才给入口」会死锁。四个分支都必须收尾（有区间 / 取数中 / 取失败 / 区间非空但解析不出），漏最后一档会落到「正在获取说明…」。**「已是最新」的判据三重**（`dshNotesLatest`）：`ok` + `empty` + **结论属于当前这组版本**（`dshNotesFresh()`）。`notes` 异步回传，换版本重查时旧的那份仍挂着，直接展示即张冠李戴；显示「已是最新」还会藏掉折叠行、连重取入口都没了。
    - **⚠️ 实装版本必须与宿主取数时用的那一份同源**（`dshInstalledVer` = 宿主广播的 `resolved`）：早先界面按 `dsh.source === 'global' && dsh.globalVersion ? dsh.globalVersion : dsh.installed || dsh.globalVersion`，实则 `dsh.installed` 是「插件目录」那份、**不含全局安装**。全局装 dsh 时两边版本不同 → `resolvedTarget` 对不上 → `dshNotesFresh` 恒 false → 永远停在「正在获取说明…」。rc.2 两种口径都落区间模式掩盖差异，只在「选比实装新的中间版本」时现形。
    - **⚠️ 新鲜度键必须与宿主逐字镜像**（`dshNotesResolved` ↔ 宿主 `loadNotes` 的 `newerByTime(target, installed) ? installed + '->' + target : target`）：所选比实装新 → 区间模式、上界随实装走，键带实装版本；所选不高于实装 → 单版本模式，只看所选那版、与实装无关。**「谁更新」按发布时间判**（`times`，见第六节）—— 按 semver 会把官方给旧分支补发的、号更小但更晚的补丁判成旧版，两侧「一致」却一致判错。界面**不复刻「取区间上界」的算法**：复刻要两处各改，漂了即「恒 false、重取也没用」。
    - **⚠️ 展开期间版本一变就重取**（`watch([dshInstalledVer, dshTargetVersion, () => dsh.notesBusy])`，触发条件 `!dshNotesFresh()`）：换下拉只落盘配置（`patchCfg`），**中间没有任何操作会经过「展开」入口** —— 即「切换版本后都要收起再展开才能获取」。只在展开时生效：说明是附注信息，不点开不该占一趟网络；收起态下版本变了不重取，展开那一下 `dshToggleNotes` 会补取。
    - **⚠️ 取数期间另挂 600ms 快轮询**（`dshNotesFastTimer`）：结果靠 4s 一跳的 `dshPolling` 回传，而说明常要数秒，4s 去接平均多等半格。快轮询只在 `notesBusy` 为 true 期间跑，落回 false 即停；真失败 / 超时仍有 4s 兜底。
    - **「查询可用版本」不再顺带取说明**：`listVersions()` 里的 `loadNotes(true)` 已去掉，改由前端展开「版本说明」时按需发起（多数时候用户不展开）。宿主侧 `loadNotes` 的入口语义（先 `syncConfig()`、空区间零请求、`notesDirty` 补跑）见 `lib/dsh-notes.js` 与 `lib/dsh.js`。
  - **⚠️ 设置页的版本比较是宿主 `newerByTime` 的副本，必须同样按发布时间**（`dshVerNewer`，`dshVerSemver` 为 semver 兜底）：设置页不能 `require` 宿主模块，只能各持逐字镜像（同 `isNewer`/`cmpVer` 副本）。**两处消费都按 `times` 判**：官方会给旧分支补发版本号更低的补丁（`0.1.5-rc.3` 晚于 `0.1.6-alpha.2`），semver 会判反：① `dshTargetVersion` 的 `'newest'` 哨兵取列表里**最晚发布**的版本（清单按 npm 发布序，必须逐项比较，不能取末位；与宿主 `maxVersion` 同口径，否则界面选的「最新（含测试版）」和宿主实装的对不上）；② `dshNotesResolved` 拼新鲜度键时判「所选是否比实装新」—— 判反会让键与宿主对不上、版本说明卡在「正在获取说明…」。`dsh.versions` 兜底对象要带 `times:{}`（老快照没有时靠空对象退回 semver，不能留 `undefined`）。
  - **版本下拉的标记（`dshVersionOptions`）**：先把「同一版本号上的各种标记」汇总再生成选项，避免边判边 push 时 `seen` 去重吃掉后到的标记。三个标记来源——**已安装**（判据是 `dsh.resolved` = **实际在用**那份，并按 `dsh.source` 细分「全局已安装」/「插件目录已安装」；**不能判 `dsh.installed`**，那是「插件目录那份」，全局安装时恒为空、选项上无标记）、**已选**（`cfg.dshVersion`）、**latest 标签**（`versions.latest`）；同一版本号可能同时带多个标记（如 `1.6.0-alpha.2（全局已安装，latest 标签）`），有标记的版本优先提到列表前。下拉按宿主给的顺序倒序展示（npm 发布序，不按发布时间重排）。
  - **查询提示会自行清掉**（`dshQueryVersions`）：宿主的 `dshListVersions` 是异步的，查询期间挂「正在查询可用版本…」，并挂 2s/5s/9s/12s 四个探测点 —— 每次先 `dshStatus()` 取快照，**取到 `versions.latest` 即清提示**（`dshStatus` 是通用轮询入口、成功时不碰 `dshFlash`，不清会一直挂）；用令牌 `dshQueryDone` 防止上一轮兜底定时器清掉下一轮刚设的提示；只清「还是我发的那条」（比对 `DSH_QUERY_MSG`）以免覆盖用户等待期间其它操作的消息；12s 仍无结果则报红字超时。
  - **异步动作（启动 / 重启 / 更新）必须有终态收尾**：这三个动作用 `dshDo` 发起 —— 宿主同步返回**半成品快照**（`busy` 刚置上），真正的结果靠之后轮询拿。早先点完只写占位消息便无下文：成功只进折叠日志、失败只写卡底 `dsh.error`，占位消息永远挂着，用户**无从判断成败**。`dshQueryVersions` 早有「令牌 + 兜底点位」清提示的写法，唯独这三条漏了。修法：`dshAsync`（`active/token/wasBusy/idleTicks/action/before`）在 `dshDo` 里挂载，`dshSettle()`（由 `dshStatus()` 尾部调用）盯 `dsh.busy` 落回空后**改写 `dshFlash` 为终态结论**（更新成功报「更新完成：v1.6.0 → v1.7.0」，失败则清掉占位消息、把话语权交给卡底的 `dsh.error` 红字并自动展开日志）。
    - **⚠️ `busy` 在更新途中会短暂清零，判据必须是「连续两轮空闲」**：`update()` 先置 `'update'`，`installDsh()` 开头把它重置，重试提权时又置回 —— 一看到空就宣布结束会在「正在结束旧进程」的间隙误报。用 `wasBusy` 区分：见过 `busy` 的空闲一轮即可收尾，没见过（动作在两次轮询之间就跑完了、或首次快照即终态）要两轮。
    - **⚠️ `'versions'` 不参与结束判定**：它是另一条独立链路，混进来会让更新没跑完就被判结束。
    - **⚠️ 收尾不能只靠固定点位定时器**：更新走 github / tarball 来源时要现场 clone + 构建，**可能跑几分钟**，早先最远只到 90s，超时后无人接着查 = 又丢结果。现在 `dshDo` 的点位（`[5s, 20s, 45s]`）只负责早点刷新界面，**真正的收尾交给 4s 常规轮询**（`dshPolling`，仅在「开发者」Tab 激活时跑）。
    - `stop` **不参与**：它是同步语义，结果由下一次快照直接给出；且它与「重启」的对话框延迟口径不同（`dshDo` 里 `restart` 2.5s/6s、`start` 0.8s 才复查）。
    - **⚠️「启动成功」用 `dsh.ready`，绝不用 `dsh.running`**：**「端口有人在监听」不等于「起来了」** —— activation-audit 失败时 web 端口**已经被 bind**，**然后**才拒绝整个 composition 并退出。本项目同构：`dsh.running` 只表示「我们 spawn 的子进程还活着」，进程起来但组装失败、正准备退出时它**同样是 true** → 拿它报「已启动」就是报假成功。`dsh.ready`（`watchReady` 观测到配置端口（`config.dshPort`，默认 3080）真正开始监听）才是唯一判据。
    - **⚠️ 进程类动作（启动 / 重启）必须留「宽限等待」**：`busy` 落空时 dsh 往往还没监听端口（还要十几秒），此时 `ready` 仍 false，就此收尾会误报「启动未成功」。所以 `dshAsync.deadline`（`start`/`restart` 为 +90s，`update` 为 0 不等待）内只要没出错且未 ready 就重置 `idleTicks` 继续等。取 90s 是让「起不来」早点有结论（`watchReady` 给到 3 分钟）。
    - **⚠️「更新成功」不要求 `ready`**：更新只保证**装到了新版本**（判据是回读磁盘，见下条），未必把 dsh 拉起来 —— 用 `ready` 当判据会把「装成功但没启动」误报成失败。对应文案也分岔：「更新完成，dsh 已用新版启动」/「更新完成（新版本已装好，下次启动生效）」。

  - **查询提示会自行清掉**（`dshQueryVersions`）：宿主的 `dshListVersions` 是异步的，查询期间挂「正在查询可用版本…」，并挂 2s/5s/9s/12s 四个探测点 —— 每次先 `dshStatus()` 取快照，**取到 `versions.latest` 即清提示**（`dshStatus` 是通用轮询入口、成功时不碰 `dshFlash`，不清会一直挂）；用令牌 `dshQueryDone` 防止上一轮兜底定时器清掉下一轮刚设的提示；只清「还是我发的那条」（比对 `DSH_QUERY_MSG`）以免覆盖用户等待期间其它操作的消息；12s 仍无结果则报红字超时。
  - **异步动作（启动 / 重启 / 更新）必须有终态收尾**：这三个动作用 `dshDo` 发起 —— 宿主同步返回**半成品快照**（`busy` 刚置上），真正的结果靠之后轮询拿。早先点完只写占位消息便无下文：成功只进折叠日志、失败只写卡底 `dsh.error`，占位消息永远挂着，用户**无从判断成败**。`dshQueryVersions` 早有「令牌 + 兜底点位」清提示的写法，唯独这三条漏了。修法：`dshAsync`（`active/token/wasBusy/idleTicks/action/before`）在 `dshDo` 里挂载，`dshSettle()`（由 `dshStatus()` 尾部调用）盯 `dsh.busy` 落回空后**改写 `dshFlash` 为终态结论**（更新成功报「更新完成：v1.6.0 → v1.7.0」，失败则清掉占位消息、把话语权交给卡底的 `dsh.error` 红字并自动展开日志）。
    - **⚠️ `busy` 在更新途中会短暂清零，判据必须是「连续两轮空闲」**：`update()` 先置 `'update'`，`installDsh()` 开头把它重置，重试提权时又置回 —— 一看到空就宣布结束会在「正在结束旧进程」的间隙误报。用 `wasBusy` 区分：见过 `busy` 的空闲一轮即可收尾，没见过（动作在两次轮询之间就跑完了、或首次快照即终态）要两轮。
    - **⚠️ `'versions'` 不参与结束判定**：它是另一条独立链路，混进来会让更新没跑完就被判结束。
    - **⚠️ 收尾不能只靠固定点位定时器**：更新走 github / tarball 来源时要现场 clone + 构建，**可能跑几分钟**，早先最远只到 90s，超时后无人接着查 = 又丢结果。现在 `dshDo` 的点位（`[5s, 20s, 45s]`）只负责早点刷新界面，**真正的收尾交给 4s 常规轮询**（`dshPolling`，仅在「开发者」Tab 激活时跑）。
    - **⚠️ 轮询启停必须覆盖「挂载时 Tab 就已经是 dev」**（2026-11-12 修，用户报「用 Edge 打开了、dsh 明明起来了，设置页 dsh 卡一直显示启动中」）：`dshPolling` 由 `watch(activeTab)` 启停，而 `activeTab` 初值取自 `localStorage` 的 `whale:lastTab` —— 上次停在「开发者」的用户重开设置页时 Tab 一上来就是 `dev`，watch 不触发、轮询永不启动，卡片状态冻结在首帧：点「启动」后 `dshApply` 写进 `running=true / ready=false`，之后再没有任何一次快照，界面就一直停在「启动中…（3080 未就绪，已 N 秒）」，而宿主 `state.ready` 早已为 true。修法：把 watch 回调提成 `dshSyncPolling()`，`onMounted` 里按当前 Tab 补调一次。**watch 本身不能加 `immediate`**：回调引用了文件后段才声明的 `dshAutoRefresh` / `dshQueryVersions`，立即执行会踩 TDZ。窗口重新可见 / 聚焦那一路由 App.vue 的 `onWindowActive()` 兜底（`activeTab === 'dev'` 时补 `dshStatus(true)`）。与上一版宿主侧的就绪判定（见下）是两条独立的链路，别只修一边。
    - `stop` **不参与**：它是同步语义，结果由下一次快照直接给出；且它与「重启」的对话框延迟口径不同（`dshDo` 里 `restart` 2.5s/6s、`start` 0.8s 才复查）。
    - **⚠️「启动成功」用 `dsh.ready`，绝不用 `dsh.running`**：**「端口有人在监听」不等于「起来了」** —— activation-audit 失败时 web 端口**已经被 bind**，**然后**才拒绝整个 composition 并退出。本项目同构：`dsh.running` 只表示「我们 spawn 的子进程还活着」，进程起来但组装失败、正准备退出时它**同样是 true** → 拿它报「已启动」就是报假成功。`dsh.ready`（`watchReady` 观测到 dsh **实际运行的那个端口**（`state.runPort`，未启动时退回配置端口 `config.dshPort`，默认 3080）真的在监听）才是唯一判据。
    - **⚠️ 进程类动作（启动 / 重启）必须留「宽限等待」**：`busy` 落空时 dsh 往往还没监听端口（还要十几秒），此时 `ready` 仍 false，就此收尾会误报「启动未成功」。所以 `dshAsync.deadline`（`start`/`restart` 为 +90s，`update` 为 0 不等待）内只要没出错且未 ready 就重置 `idleTicks` 继续等。取 90s 是让「起不来」早点有结论（`watchReady` 不设上限，起来晚也能补上就绪）。
    - **⚠️ 就绪判定必须有三条正面证据，且绝不比 `probe.port`**（2026-11-11 修，用户报「一直显示启动中」）。`watchReady()` 每 1200ms 一轮（**首轮立即执行，不再干等 1200ms**），`confirmReady()` 有三个来源：① **本机 HTTP 探活**（`dshWeb.alive(host, runPort || port, 800)`，303 / 401 / 404 都算应答）—— 语义最直接（能应答＝已 listen），不依赖 pid / 进程树，也**不排 `probe.busy` 那道闸门**；② `probePort` 探到监听者属于**本插件进程树**（`pid === state.pid || probe.selfOwned`）；③ `captureWebUrl()` 从 stdout 抓到带 token 地址（该行只在 listen 之后才输出）。
      - **⚠️ 判据里不许出现 `probe.port === state.port`**：`probePort` 在 `busy` 闸门忙时只回放**缓存**，而缓存里的 `probe.port` 可能还停在换端口前的旧值 → 判据恒假 → 界面永久「启动中…」。这正是上一版的真凶，别改回去。端口真被别家抢占时，我们的 dsh 会 EADDRINUSE 退出，`exit` 里的 `clearReady()` 会清掉，不会误置就绪。
      - `configure()` 换端口时**同时重置 `probe.port`**（否则旧值残留，任何按它比对的判定都会失效）。
      - `confirmReady()` 开头有 `if (!state.child || state.stopping) return`：结束途中服务可能还能应答，不加守卫会让界面从「正在结束…」跳回「运行中」。
      - `bindOutput()` 同时监听 `stdout` / `stderr` 的 `'error'`：不挂时管道读错会抛未捕获异常，且 token 地址这条证据会静默失效。
      - 配套两条：
      - `parsePortPid` 按**最后一个冒号**切出纯端口号精确比较，不再用 `indexOf(':' + port)` 子串匹配 —— 后者把 `127.0.0.1:30800` 也算成 3080 在监听。
      - `flushProbe` 回放 `waiters` 前先置 `probe.busy = false`（否则被回放的 `watchReady` 在回调里再调 `probePort` 会把自己重新压回队列，本轮 flush 已结束 → 队列只增不减、`probe.pid` 永不更新）；`probePort` 排队时另挂 8s 兜底计时器，保证 `resetProbe()` 清空队列等任何情况下调用方都能拿到回调、闸门不会永久关闭。
      - **⚠️ 启动期状态必须能自愈推送，dsh 自己的输出必须落盘**（2026-11-12 修，用户第二次报「外部 10s 起来了，挂件里几分钟还显示启动中」）。三处配套：① `pushLog()` 原先**只写内存** `state.log`（只喂界面快照），`%TEMP%\whale-debug.log` 里只剩「已启动」一行 —— dsh 后续输出、「已就绪」「dsh 已退出」全无痕迹，两次复发都因此拿不到证据；现在它同时 `log()` 落盘（`log()` 自带 token / `sk-` 掩码，不会泄露页面 token）。② `broadcast()` 的 `catch` 不再留空，改为 `logErr('[whale][dsh] 状态广播失败', …)` —— `snapshot()` 抛错与推送失败必须留痕，否则界面停旧状态且磁盘空白。③ `watchReady()` 的 `tick` 在 `!state.ready` 时**每拍补推一次完整快照**：挂件不轮询、只靠 `whale:dsh` 推送，推送丢一次就永久停在「启动中…」；补推让它自愈（`confirmReady()` 清表后即停，不空转）。挂件 `dshRender()` 的「启动中…（X 未就绪）」同时追加已等待秒数（读快照 `startedAt`），真卡住时用户能看到计时在走，而不是误以为界面冻死。
    - **⚠️「打开页面」必须用带 token 的原文地址，且内置浏览器需插件注入 Cookie**（2026-11-11 结论）。dsh web 的鉴权是两步：① `GET /?token=xxx`（token **每次启动都会变**）→ `303` + `Set-Cookie: dsh-auth-<nonce>=…; HttpOnly; SameSite=Strict; Path=/`；② 之后的页面资源与 `/api/*` 全靠这条 Cookie。**`token` 只对首页那一次跳转生效，不带 Cookie 直接访问 `/api/*` 一律 401**。地址由 `captureWebUrl()` 从 stdout 抓进 `state.webUrl`（`clearReady()` 启动 / 停止时清空），`pageUrl()` 只给它；`webUrl()` 是不带 token 的兜底。

      - 对策：`dsh-web.js` 在 `openInBuiltin()` 前先由 Node 侧取 Cookie，交给纯函数叶子 `dsh-cookie.js` 的 `parseSetCookies()` 转成 `CookieDetails`，再 `ub.setCookies(list).goto(url).run(WIN_OPTS)`（同一队列，顺序执行）。取不到 / 注不进一律**照常无 Cookie 打开**并留日志，不阻断用户。
      - **⚠️ 必须打页面地址（`/?token=…`）取 Cookie，不能打 `/connect`**（2026-11-11 二次修正，修用户报的 「dsh web authentication required; reopen the URL printed by dsh web.」）。读 `dsh-client-connection` 源码确认，dsh 有**两套** cookie 校验，而两条 cookie **同名**（`dsh-auth-<authority>`，由 `cookieName(authority)` 按 Host 推导），浏览器里只能存在一条：
        - `GET /?token=…` → `303`，payload **version 1**（无 `id`）；`isAuthenticated()` 判 `=== COOKIE_PAYLOAD_VERSION`（常量 = 1）→ **只认 v1**；页面 index（`authorizeIndex()`）与 websocket（`admitConnection()` → `admit()`）**都首选它**。
        - `GET /connect?token=…&interactions=…` → `302` 到 `./api/remote.mux`，payload **version 2**（含 `publishPeer()` 给的 operator `id`）；只被 `authenticateApi()` 认可。
        - `admit()` 的顺序是**先 `isAuthenticated`（v1）**、不过才 `authenticateApi`（v2）。所以**一条 v1 就够页面也够 ws**；注入 v2 反而让页面 index 直接 401（`writeUnauthorized()` 那句原文）—— 上一版正是从 `/connect` 取 v2，才把页面打成 401。**别再改回 `/connect`。**
      - **⚠️ 注入成功后保留 `?token=` 打开，不要剥成裸地址**（与上一版相反）：上一版剥 token 是怕带 token 的 `GET /` 再发一条同名 v1 顶掉注入的 v2；现在注入的就是 v1，再发一条同样的 v1 不会打架。反之，万一 uBrowser 没认注入的 Cookie，带 token 打开还能落到页面外壳（接口 401 但界面出得来），裸地址则直接 401 白屏。
      - **⚠️ 不能用全局 `fetch`**：preload 里 `fetch` 抛错（日志表现为 `没取到认证 Cookie HTTP 0`），改用 Node 内置 `http.request`。
      - **⚠️ 内置浏览器内核是 Chromium 108，缺 `AbortSignal.any` → 必须注入 polyfill**（2026-11-12 定因，修用户报的「左下角一直显示重新连接中」）。uTools 7.8.0 的 uBrowser 页面 UA 实测 `Chrome/108.0.5359.215`，而 dsh 前端用了 Chrome 116+ 的 `AbortSignal.any`：`dsh-api-gateway` 的 `pumpEvents` 在**建流之前**就 `AbortSignal.any([signal, failed.signal])`，108 里它是 `undefined` → TypeError → 每个 generation 立刻失败 → `ConnectionController.loop()` 无限重试，指示器永远停在 `data-phase="connecting"`。同一地址用 Edge（新内核）完全正常，差别只在内核版本。取证：页面自己的 WebSocket 全部 `open:true` 但 `sent:0`（一帧都没发出去就被 `close(4000)`），而插件另开一条原生 WS 手发 `$events` open 帧立刻收到 `ready` —— 服务端与鉴权都正常，失败发生在发帧之前。对策：`dsh-web.js` 的 `patchPage()` 经 `ubrowser.evaluate` 在页面里补 `AbortSignal.any` / `Promise.withResolvers` / `Symbol.dispose` / `Array.prototype.toSorted|toReversed|with` / `Object.groupBy`（全部带存在性判断、用 `defineProperty` 装，重复执行无副作用，将来 uTools 换新内核后自动变空操作），10s 后回读连接指示器落一行 `内置浏览器 polyfill` 日志（按 `data-phase` 的 `connecting` / `disconnected` 值筛 —— 会话根节点也有 `data-phase`（`settling` / `hero` / `active`），裸选择器会抢到错元素；`phase: "gone"` = 指示器没渲染 = 已连上，仍是 `connecting|…` 才是没修好）。evaluate 只能在页面 load 之后跑，但连接控制器会一直重试，补上后下一轮重试自然就通 —— **别删这段**，也别以「新版 uTools 可能不需要」为由提前移除。
    - 排查顺序（内置浏览器报 `dsh web authentication required` / 页面数据全无时）：① 日志有没有「已捕获带 token 的页面地址」（没有 → stdout 没抓到，看下一条）；② 有没有「取到认证 Cookie」（没有 → 看同条日志的状态码：`HTTP 0` = 请求没发出去或超时，`HTTP 401` = token 过期，重启 dsh 后地址会换）；③ 取 Cookie 打的是不是**页面地址**（打 `/connect` 会拿到 v2、页面必 401）；④ 有 v1 Cookie 仍 401 → uBrowser 未认注入的 Cookie（此时带 token 打开至少还能出外壳）；⑤ 页面出得来但一直「重新连接中」→ 看日志「内置浏览器 polyfill」行的 `applied` 是否含 `AbortSignal.any`、`phase` 是否 `gone`（`applied` 为空且 phase 仍 `connecting|…` = 内核还有别的缺 API，按 `feat` 探针继续补）。
    - **⚠️「更新成功」不要求 `ready`**：更新只保证**装到了新版本**（判据是回读磁盘，见下条），未必把 dsh 拉起来 —— 用 `ready` 当判据会把「装成功但没启动」误报成失败。对应文案也分岔：「更新完成，dsh 已用新版启动」/「更新完成（新版本已装好，下次启动生效）」。

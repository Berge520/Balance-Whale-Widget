  - **⚠️ 写坏了 dsh 不报错，必须回读核验**：往 patch 写不存在的 id，dsh 只在 stderr 打 `patch: entry "X" not found`，**退出码仍是 0**；安装 / 卸载 / 禁用完成后都要回读磁盘确认。
  - **⚠️ 回读核验已有四道，第五道「装了 ≠ 生效」（`activationOf` + `dsh-dump.js` 的 `verifyActivation`）**：前四道（`!hit` / `blockedByPolicy` / `downgradedBy` / `mismatchResolved`）判的是**依赖层面**「包在不在、版本对不对」，**答不了「dsh 认不认它」**。dsh 有三个命名空间（见 [10-settings-dsh-diag.md](10-settings-dsh-diag.md)「C2 判据踩坑」第一张表）：`dependencies` 的 npm 包名、`dsh.profile.bundles` 的挂载名、patch 的 `- id:` 组装树注册 id，只比包名会漏判。
    - **第五态 `skipped` 来自本机实测**：`dsh --profile web --dump-config` 输出打过 `dsh: skipping profile bundle "dsh-find-plugin": Error: Plugin dsh-find-plugin@0.4.0 is incompatible with dsh 0.2.1-alpha.2: peerDependencies {...}`：**装上了、依赖回读也正确，但 dsh 加载期主动跳过了它**。**与 C2 那条 `patch: entry "config-manager" not found` 区分**：后者是 patch 条目对不上组装树，前者是包被加载期否决；`parseSkipWarnings` 与 `parseDshWarnings` 是两个独立解析器，消费方也不同（not-found 进配置转储卡，skipping 进安装结果卡）。这是「装了但没生效」的真实形态（`pnpm add` 退出码 0、文件都在）。判据沿用 C2 定案（[10-settings-dsh-diag.md](10-settings-dsh-diag.md)「采信 dsh 说了什么」）：**只抽取 dsh 自己打的 `skipping profile bundle` 行，不自己造清单**。
    - **五态语义**（`state`，顺序敏感，见 `dsh-dump.js` `verifyActivation`）：
      | state | 含义 | 触发条件 |
      |---|---|---|
      | `active` | 已装配进生效树 | 三源并查任一命中且未被 dsh 跳过 |
      | `skipped` | dsh 加载期主动跳过 | dsh 打了 `skipping profile bundle "<名>"` |
      | `pending` | 装了但配置转储早于本次安装 | 树里找不到 **且** `dump.at < installAt` |
      | `shadowed` | 树有效、找不到它（装了没被装配） | 树里找不到且 dump 不陈旧 |
      | `unknown` | 任何判据都读不到 | 没有 npm 名 / 转储失败 / 没解析出分节 |
    - **判据三源并查**（`sectionBundles`，任一命中即算已装配）：① 分节标题的包名（`# == dsh-whale-widget`）② 条目 `name:` ③ patch 的 `- id:` 注册 id。**⚠️ 不能只比「分节标题 == 包名」**：实测 `dsh-better-sidebar` **已生效**，但分节标题是 `# == dsh-better-sidebar, patched by …\cordis.patch.yml`、挂载 id 是 `better-sidebar`（patch 里 `- id: better-sidebar`），精确相等会把**合法生效**判成「未生效」；先剥 `patched by` 后缀，并把条目 `name` / patch id 一并纳入。三源都要归一化（去 `@scope/` 前缀、小写、去首尾空白）：`@linxin666/dsh-web-all` 与 `dsh-web-all` 两种写法都出现过。
    - **⚠️ 不得复用 `entries` 当已知清单**（[10-settings-dsh-diag.md](10-settings-dsh-diag.md)「C2 判据踩坑」教训）：`--dump-config` 的 `entries` 本身不完整（`mnemon-bundle` 的 `config:` 内层嵌套子条目，`parseDump` 认不出），拿它当「生效树里有哪些」的依据必然漏判；`sectionBundles` 只收**分节标题 + 条目 name + patch id** 三个来源，**绝不**拿 `entries` 的键反推「树里没有 = 没生效」。
    - **⚠️ 读不到 bundle 判据时必须 `unknown`，绝不能降级 `shadowed`**（[10-settings-dsh-diag.md](10-settings-dsh-diag.md)「必须区分『拿不到』与『空数组』」同型陷阱）：转储失败 / 没解析出任何分节时，会因「三源都没命中」误报 `shadowed`，把「不知道」说成「没生效」。`sectionBundles` 用 `complete` 字段显式表达「有没有解析出分节」，`complete !== true` 一律退 `unknown`。
    - **⚠️ `skipped` 优先于 `active`**：跳过是 dsh 加载期的明确否决；某些版本先登记后跳过，此时以「被跳过」为准；`verifyActivation` 里 skipped 判定必须排在「三源命中」之前。
    - **⚠️ 陈旧转储 → `pending` 而非 `shadowed`**：刚装完、转储还是安装前缓存时树里找不到，报 `shadowed` 是假阴性；`activationOf` **强制重跑一次生效树**（`dumpEffective`，不吃 `collectDshDump` 的 60s 缓存）。**⚠️ 传给 `verifyActivation` 的 `dump.at` 必须取「本次转储*发起*的时刻」**：它用 `snap.at < installAt` 判旧状态，取返回后时刻则恒 `at > installAt`、该分支永不触发（将来改回复用缓存就会把陈旧误报成 `shadowed`）。取发起时刻后：强跑新转储不判 pending，真拿到旧快照判 `pending`。
    - **⚠️ `activationOf` 只读、只看这一个包、失败不阻断**：单跑生效树（不跑默认树）省一半时间，`DUMP_TIMEOUT_MS = 8000` 上限；读转储失败时 `logErr` 留痕并退 `unknown`，**不让第五道校验否掉「已经装好了」这个事实**：结论是「装好了，但无法确认生效」。
    - **⚠️ 没有 npm 名的来源（纯 `github:` / tarball）直接 `unknown`**：`activation` 判据靠包名比对，spec 反查不出 npm 名时无从判定；给 `unknown` + 「该来源没有可用的 npm 包名，无法核对生效状态」，**不假装 active**。
    - **⚠️ 仍不自动重启 dsh**（口径同 [10-settings-history-dsh.md](10-settings-history-dsh.md) 的 `needsRestart`）：`needsRestart: true` 照旧回传，界面提示 + 「重启 dsh」按钮由用户决定时机：重启会掐掉用户正在跑的会话。`pending` 的文案是「配置转储早于本次安装，重启 dsh 后生效」。
    - 单测在 `test/dsh-dump.test.mjs`（本卡相关）：`parseSkipWarnings`（真实行 / 空数组 / ANSI + 去重）、`sectionBundles`（三源 + 剥 `patched by` + 去 scope / 归一化 / 空输入 `complete:false`）、`verifyActivation`（`active` / **反例钉子** `dsh-better-sidebar` 挂载名 ≠ 包名仍判 active / `skipped` / `pending` / `shadowed` / 边界 `at == installAt` 仍判 `shadowed` / **反向钉子**「读不到必 unknown」四种情形 / skipped 优先于 active）。类型侧 `services.d.ts` 新增 `DshMarketActivation`（五态 + `pkg` + `reason`）、`DshMarketInstallResult.activation?`、`DshDumpResult.bundles?` / `skipped?` 与 `DshDumpBundles` / `DshDumpSkip`。
  - **spec 与 profile 名都过白名单**（`validPkgSpec` / `validPkgName` / `validProfile`）：spec 来自**远端目录**，不校验就等于让远端把 `--prefix` 塞进命令行。`validPkgSpec` 比 `validPkgName` 宽（放行 `github:owner/repo(#ref)?` 与 `https?://…(.tgz)?(?query)?`），但**不是「放行任意字符串」**：仍禁 `-` 开头 / 空白换行 / 引号 / shell 元字符 / 反斜杠，上限 214 字符。**卸载仍只认 `validPkgName`**（`package.json` 的键是 npm 归一后的名字，用 spec 去 `pnpm remove` 匹配不上）。
  - **加载失败降级到离线副本**（`settings.marketCatalog`）：抓取失败时不报「加载失败」，改回 `ok:true` + `from:'cache'` + `stale:true` + `staleReason`，用 `dbStorage` 里上次成功的副本（`whale:dshMarket`，只存 `{at,updated,source,categories,plugins}`）继续展示。
  - **内存缓存 TTL 60 秒**（`CACHE_TTL_MS`）：目录每天才刷新，60s 足够挡住反复点击；**「强制重抓」**（`dshMarketLoad(true)`）传 `force: true` 绕过。**缓存键 = 参与竞速的来源集**（`sources.map(s => s.key).join('|')`）：改了自定义 URL **或换了 registry** 就该重抓，不能拿上一家的目录冒充。**⚠️ 不再有「按来源重试」**（旧 `MAX_TRY = 2` 已删）：竞速下单源失败即出局，重试只拖住整次加载。体积上限 `MAX_BYTES = 16MB`（防被劫持镜像撑爆内存）。
  - **⚠️ 已装状态要预先算好，别在模板里逐次调**（`dshMarketHitMap` / `dshMarketHitAt`）：模板里要读它多次（已装 / 已禁用 / 未写 patch / 按钮 `disabled`…），上百条即数千次调用，每次还要重建候选名数组 + 遍历 `package.json` 全部键。改法：`dshMarketHitMap` 这个 `computed` 按目录数组下标预计算（与 `dshMarketList` 同源、索引对齐），模板 `v-for="(p, pi)"` 用 `dshMarketHitAt(pi)` 取。

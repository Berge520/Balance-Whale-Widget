- **「dsh 故障诊断」卡片**（「开发者」Tab，位于「dsh 用量统计」与「Codex 会话统计」之间）：**整卡默认收起**（`devFolds.diagnose`，标题即开关，走同一个 `toggleDevCard`），**首次展开才跑**（`devStatsLoaded.diagnose` 只置一次）—— 五项检查都要读本地文件（C1 还要遍历 `node_modules`）。卡片头右侧摘要（`diagnoseSummary`）三段：没读过显示「点击展开诊断」、dsh 未装显示「dsh 未安装」、有结论显示「N 项通过 · M 项异常」（`M` 含 C5「查不出归属」那类 warning，见下）。按钮三枚：**「重新诊断」**（`diagnoseRefresh()`，TTL 内复用）、**「强制重跑」**（`diagnoseRefresh(true)`，绕过 60s TTL）与**「复制诊断信息」**（`diagnoseCopy()`，复制**未截断**的完整结果 + 环境快照）。
  - **⚠️ `diagnoseDsh()` 是 Promise，必须 `then` / `await` 取结果（真实 Bug）**：C5 端口探测走 `probePort()` 的 `execFile` 回调，是它异步的根源。`dshUsageSummary()` / `codexSummaryCached()` 同步返回；**`codexSummary()` 自 v-codex 异步化起也返回 Promise**（`CodexView.vue` 的 `codexRefreshRun` 已改 `await`，详见 07 分片「Codex 扫描已是全异步」）。早先设置页把 `diagnoseDsh()` 返回的 Promise **直接当结果对象用**（`diagnose.value = r` 然后读 `r.error` / `r.cached`），后果：① 结果渲染不出来（字段全 `undefined`，只显示「全部通过」）；② 宿主侧同步等探测结果会占住**设置页所在的渲染进程** —— **卡在「诊断中…」且整页卡顿**。
    - 宿主侧硬约束（`settings.js`）：Promise **必须保证一定会 settle**。除 `detectPort()` 自带的 8s 超时外，`diagnoseDsh` 另加 **15s 兜底闸门**（`settled` 标志 + `done()` 收敛所有出口）—— 否则回调不回来时 Promise 永久 pending，前端 `finally` 不执行，按钮退不出「诊断中…」。
    - 设置页侧硬约束（`App.vue`）：必须 `p.then(...).catch(...).finally(...)`，`diagnoseBusy` 只在 `finally` 解锁。**不能用 `try/catch` 包同步调用**（Promise 的 rejection 不会进 `catch` 块）。
    - `readEnv()`（走 `dsh.snapshot()`，唯一同步重活）已从「进 Promise 前」挪到**探测回调内**，避免探测慢时叠加卡顿。
  - **同步读文件必须先让出一帧**：宿主侧同步读（遍历 `node_modules` / 探测端口）会卡住这次渲染，故 `diagnoseRefresh` 先 `window.setTimeout(() => diagnoseRefreshRun(force), 30)`（与 dsh 用量卡同一手法）。`diagnoseFlash` 单条消息态，文案说清「复用的 60 秒内旧结果」还是「这次刚跑完」（`r.cached`）。两枚刷新按钮必须分开（缓存 / 绕缓存），理由见转储卡的「缓存接线踩坑」。
  - **severity → 文本标记（不用 emoji / SVG）**：`diagnoseMark(item)` 返回 `[✗]`（`threw` 或含 `error` 级明细）/ `[!]`（含 `warn` 级明细）/ `[✓]`（全无明细），配 `.diag-mark` 等宽字体对齐标题起点，颜色类 `.diag-ok` / `.diag-warn` / `.diag-bad`。单项抛错按 `[✗]` 显示并带 `err.message`，不影响其余四项（宿主侧标记 `threw`）。
  - **明细截断只作用于渲染**（`DIAGNOSE_SHOWN = 5`）：每项最多渲染 5 行（`diagnoseShown`），超出显示「还有 N 项，点上方『复制诊断信息』看完整明细」（`diagnoseRestCount`）。**缓存里存的是完整结果**，不因界面省地方而丢证据。明细行 `.diag-line` 用 `word-break: break-all`（路径与报错原文可能很长，不许撑破卡片），`hint` 跟在后面以 `→` 引出「下一步怎么办」。
  - **未安装空态**：`!diagnose.env?.installed` 时不渲染结果列表，只给一行 `hint` 指着「先在『dsh』卡片里启动一次（会自动下载安装）」。判据取 `env.installed`（宿主 `readEnv()` 里 `snap.installed || snap.resolved`）—— **不是结果对象的顶层字段**，早先 UI 写成 `diagnose.installed` 被 `vue-tsc` 拦下。**`env` 可为 `null`**（读环境失败 / 超时兜底），此时不冒充「未安装」：模板用 `v-if` / `v-else-if` **三道**分支各自收尾（整轮失败 / 未安装 / 已安装；原先误写成两个并列 `v-if`，多出一个无主的 `</template>`，且 `env` 为 `null` 时两道都不命中 → 渲染成空白卡），`diagnoseSummary` 与 `diagnoseEnvText()` 都先判 `env` 是否存在。
  - **底部环境快照**：`diagnoseEnvText()` 拼「Node x · dsh y（来源）· profile z · $DSH_HOME 路径」，任一读不到显示「未知」而不留空白（留白会被当成漏渲染）。
  - **卡内 `.fold` 「说明」**（`diagnoseFolds.help`，默认收起）：逐条解释五个检查项的症状与处置 —— 重复模块（profile 的 `node_modules` 里装出同版本 `@deepseek-ai/*` → cordis 认成两份包、报 `prompt section "deployment:persona" is already registered`，所有 preset 挂载失败，每次升级全局 dsh 都可能复现）、patch 条目（`cordis.patch.yml` 里 `- id: X` 必须真存在于组装树，否则报 `patch: entry "X" not found` 直接起不来）、dsh 端口（即 `dshPort`，默认 3080；被非 dsh 进程占用则起不来；已有 dsh 在跑则不必再启。**个别系统查不出进程归属 → `[!]` 并附原因，那是「没查出来」不是「查出来有问题」**）、以及「只读」承诺（不修任何东西、不写 dsh 任何文件，结果缓存 60 秒）。

  - **⚠️ 目录是「每日快照」，目录说「已是最新」不等于真是最新**（`dshMarketRegistryLatest`）：目录（镜像的 `dsh-plugin-catalog` / 官方 `plugins.json`）每天才由上游发布一次，每条写的 `version` 只是**发布那一刻**的值。**实测**：目录写 `1.61.0`，registry 上早已是 `1.65.1`。于是基于目录的「可更新」判断在滞后窗口内**必然判不出来** —— 数据源性质，不是 bug，任何客户端看到的都是同一份旧快照。
    - **界面只在卡片顶部给一个按钮，查「当前分页展示的插件」**：每行一个按钮会喧宾夺主，用户只需核实「这一页整体是否落后」。故收敛成顶部 `.mkt-latest-bar` 里**一个**「查官方最新版」按钮，点一次只查 `dshMarketPageList`（当前分页）。`pkg` 取 `DshMarketPlugin.npm`，**剥不出的 github / tarball 来源跳过不给**（npm 上无 manifest，查了必然 404，与 `dshMarketCompatable` 同口径）；`dshMarketLatestable()` 即此闸门，`dshMarketLatestTargets` 是其 computed 列表。结果按 `spec` 存进 `dshMarketLatest`（`Map`），与 `dshMarketUpdates` / `dshMarketCompat` 同口径。**⚠️ 范围必须写死在按钮旁文案里**（`本页 N 个可查（仅列出的 npm 来源）· 会联网`）：查的是**当前分页条目**，既非「已装清单」也非整个目录。
    - **⚠️ 同包多条目要按包名去重再回填**：宿主已按包名去重（见下条），界面侧仍要把结论**回填给所有同 `pkg` 的条目** —— 否则同名包在目录里出现两条时，只有第一条拿得到结论，第二条永远显示「未查到」。实现是 `Object.values(results).find((x) => x && x.pkg === pkg)` 反查宿主回的那一条。
    - **⚠️ 纯手动、不进任何自动链路**：一页几十条，自动查就是一开卡片打几十个请求 —— 与「刷新目录默认零网络」同一考量。这也正是**没有**把它并进 `marketCheckUpdates` 的原因：后者刻意做成同步 + 零网络（目录由界面传回，宿主不自己联网），改成联网会一举推翻整条设计。
    - **⚠️ 翻页 / 筛选一变就清掉结论**：`watch(dshMarketPageList)` 清空 `dshMarketLatest` 与 `dshMarketLatestAt` —— 否则是**拿旧页的答案答新页的问题**。
    - **宿主侧**（`dsh-market.js` 的 `registryLatest` / `fetchRegistryLatest`）：按**包名去重**后并发拉 `{registry}/{name%/→%2F}/latest`，并发 8、单请求 8s 超时；内存缓存 5 分钟 TTL、失败冷却 60s；`clearCache()` 一并清掉这两块。scoped 包名的 `/` 必须编码成 `%2F`，否则 registry 认不出。
    - **⚠️ 滞后的基准版本必须是「实装版本优先」，不是目录版本**（`dshMarketBaseVer`）：目录是每日快照，会**落后于用户机器上已装的版本**（实装 `1.62.0`，目录 `1.61.0`）。拿目录当基准会显示成「目录 v1.61.0 → 官方 v1.65.1」，而用户真实路径是「已装 1.62.0 → 官方 1.65.1」。故基准取 `DshMarketUpdateEntry.installed`（实装），读不到才回落 `latest`（目录），清单文案写「已装 vX → 官方 vY」。
    - **⚠️ 能不能「查」与能不能「装这一版」是两道闸，必须分开**（2026-09-25 修，`dshMarketExactable`）：`dsh-web#packages/dsh-web-all` 这种 subpath 形态**查得出官方版本**（过了 `dshMarketLatestable`），但它的 `npm` 字段不是可直接 `pnpm add` 的裸包名 —— 给了「装这一版」按钮，点下去**必然失败**（宿主只对 npm 来源拼 `pkg@版本`，`#` / 路径分隔符也过不了 `validPkgName` 的正则）。故清单里这类条目**只告知、不给按钮**，替位显示「非 npm 来源，请用「更新」」（`.mkt-latest-note`）。
    - **⚠️ 三种结论必须分开说**，尤其第 ①：① `registry 版本 > 基准版本`（基准见上条）→ 在顶部汇总里计数、并在 `.mkt-latest-list` 逐条列出「已装 vX → 官方 vY」（橙黄体系，灰字混排等于白查）；② 两者相等 → 你机器上就是最新的；③ 拉失败 → 汇总里单独计「N 个没查到」，**不能**让用户误读成「已是最新」。方向比较用界面侧 `cmpVerText`（逐段比前三段），宿主不替界面下这个结论。
    - **⚠️ 按钮不随之收起**（与「检查兼容」不同）：registry 的 `latest` 会变，用户过一阵想再确证一次是合理诉求；5 分钟内命中缓存时不出站。
    - **⚠️ 查到之后可「装这一版」，且必须精确指定版本**（`exact`，`.mkt-latest-list` 每行按钮）：不改 `marketInstall` 按目录 spec 装的默认路径，而是单开 `exact: true` + `targetVersion`，宿主把 spec 拼成 **`裸 npm 包名@确切版本`**（如 `dshmarket@1.65.1`）。**必须拼确切版本**：profile 的 `pnpm-lock.yaml` 锁着 `specifier: ^1.62.0 / version: 1.62.0`，`pnpm add dshmarket` 命中 lock 复用 1.62.0，**按原 spec 重装永远升不上去**，只有确切版本进 spec 才改写 lock。三条边界：① **只对 npm 来源开放**（github / tarball 塞版本号无意义，直接拒绝并说明）；② 版本号须形如 `x.y.z`（含 `-pre` / `+build` 后缀）；③ 回读校验多一道 —— **实装版本必须逐字等于要的那一版**，不等即判失败并报出实装值（`pnpm` 退出码 0 但 lock 复用旧版最易骗过人）。
    - **⚠️ `exact` 的 dryRun 文案要与常规分开说**：常规说「目录提供 vX」，exact 说「精确重装到 vY（`pkg@y`）」—— 说错会让人以为目标版本取自目录，而 exact 的目标是用户回源查到的 registry 版本。
    - **⚠️ `exact` 的「要不要装」判定**不能问目录，要问 `targetVersion`**（用户实测报的 bug）：用户点「装这一版」要的是 registry 的 `1.65.1`，目录快照记的可能是 `1.61.0`。原实现照旧拿 `updateState(catalogVersion, realized)` 当 `changed` —— `1.62.0`（实装）比 `1.61.0`（目录）大 → `current` → `changed: false` → 回「已装 dshmarket（1.62.0），无需重复安装」，**按钮点了没反应**。根因是把「目录维度」的结论错用到「registry 维度」。修法：`changed` 分三支 —— ① 没装 → `true`；② **`exact` → 拿 `realized || hit.depVersion` 与 `targetVersion` 比，相等才 `false`**（版本读不出时取 `true`，pnpm 装同版本幂等，白等一次好过点了没反应）；③ 常规 → 沿用 `updateState`。`already` 文案随之分叉：exact 说「已经是 vX」，常规才说「已是目录里的最新版」。
  - **⚠️ `dshMarketInstall` 的 dryRun 必须比实装版本，不能只判「装没装」**（真实 bug）：声明范围 `^1.48.0` 容得下 `1.49.0`。早先 dryRun 只用 `matchInstalledBySpec` 判装没装，已装的包无论目录涨到哪版都判成 `already` / `changed:false` —— **更新这条路根本走不通**。修法：dryRun 也要 `realizedOf` 取实装版本 + `updateState` 比大小（口径与 `marketCheckUpdates` 一致，否则「列表标着可更新、点进去说已装」自相矛盾）。随之：
    - `changed` 的语义钉死为「**这次点下去磁盘真的会变**」：没装 → 变；装了但实装版本落后于目录 → 也变。
    - 界面侧 `dshMarketPreviewInstall` **必须把目录条目的 `version` 传下去**（`DshMarketPlugin.version` → `marketInstall({version})`）——不传，宿主无从判断落后与否。
    - 界面侧 dryRun 返回 `changed:true` 且该条目 `inDeps` 时，**转交更新时间线**（`action:'update'`）而不是走安装：安装入口走 `marketInstall` 的写盘分支，不带 `from` 版本、文案也说不出「从哪版到哪版」。

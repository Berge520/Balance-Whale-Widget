  - **⚠️ 安装/更新期间必须有进度反馈**：`dshMarketInstall` / `dshMarketUpdate` 要等 pnpm 退出才 resolve，github / tarball 来源靠 `prepare` 在安装时构建（clone + 装依赖 + 构建），**动辄几分钟**，早先只有静止的「写入中…」。
  - **⚠️ pnpm 输出不必新开通道**：`runPnpm` 的 `bindOutput` 已把 stdout / stderr `pushLog` 进 `state.log`，进度回显只是 busy 期间把这些**读回来**。
  - **⚠️ 读回必须走 `dshProgress()`，不能复用 `dshStatus()`**：后者每次都触发 `probePort`（起 `netstat` 子进程），1Hz 刷新几分钟等于白起大量 `netstat`；新增**同步**的 `dshProgress()`：只回 `{ lastCmd, log }`，**只读宿主内存，零子进程、零磁盘**。唯一新增 IPC（`services.dshProgress`，类型 `DshProgress`，与 `DshStatus` 分开声明）。
  - **前端实现**（`dshMarketTick` / `dshMarketTickStart` / `dshMarketTickStop`）：确认落笔时开 1Hz 定时器，一次 `dshProgress()` 刷三处：①「已耗时」（本地时钟，不依赖宿主）② 日志尾部（`dshMarketTailOf` 取 `log` 的**尾部 12 行**，全量塞 DOM 又慢又没人看）③ **「运行详情」卡**（`dsh.lastCmd` / `dsh.log`）。日志有新输出就滚到底（`watch(dshMarketLogTail)` + `nextTick`），否则停在最早那段像卡住。定时器在 `.then()` 收尾与 `onUnmounted` 都要停（持有组件闭包，不停会空跑）。
  - **⚠️ 进度必须同时喂给「运行详情」卡**（用户实测进度区没有日志）：`dsh` 快照（`lastCmd` / `log`）只在「打开 Tab / 点刷新状态 / 4s 轮询」时由 `dshStatus()` 更新，装插件的几分钟里该卡显示的是**装之前**的旧值（「最近命令：还没执行过」）；`dshMarketTick` 把 `dshProgress()` 的同一份 `lastCmd` / `log` **并进 `dsh` 这个 `reactive` 快照**（赋值即触发渲染），不新开 IPC。
  - **⚠️「执行的命令 / 实时输出」两块必须常驻占位，不能整块 `v-if` 掉**：元素时有时无会让区块高度反复跳，也让人怀疑是否在跑；无命令时显示「尚未产生：宿主还没进到起 pnpm 那一步（见下方「实时输出」的阶段说明）」，无输出时显示空态（`.mkt-progress-log-empty`，去等宽与背景以区别真输出），两块小节标签 `.mkt-progress-k`。底部提示指向「运行详情」→「查看 dsh 日志」，并说明本区块只显示最后 12 行。
  - **⚠️「建快照」这段没有子进程，必须靠宿主旁白补上**：真写分支顺序是 `dshBackup.createSnapshot()` → `installPluginPkg()`，而写 `state.lastCmd` 的 `setCmd` 在 `runPnpm` **内部**才调用：建快照期间日志流**一个字都没有**，进度区只显示静态空态，与卡死无异。
    - **修法**：`dsh.js` 新增并导出 `note(text)`：往同一份日志流（`pushLog`）播阶段旁白并发 `broadcast()`；`settings.js` 的 `marketInstall` 真写分支动手前播「开始安装 `<spec>`：先建 profile 快照（备份 package.json 等，随后才起 pnpm）」、快照建完后播「快照已建（`<dirName>`），开始起 pnpm 进程」，快照失败也播一条再中止。「运行详情」与进度区因此**从点下确认的第一秒起就有内容**。
    - **⚠️ 旁白复用子进程输出那条通道，靠约定措辞供前端识别**：`note` 刻意**不加** `$ ` 前缀（那是「正在执行的命令」的标记）。前端 `dshMarketPhaseText()` 改为**优先照读旁白**（`/快照已建|开始起 pnpm/` → 「快照已建，pnpm 正在跑…」、`/建 profile 快照|建快照/` → 「正在建 profile 快照（还没起 pnpm）…」），命中不了再按输出关键词粗判。原先「空输出就是在建快照」的推测已删：pnpm 在跑时还说「在建快照」更糊涂。
    - `test/settings-allowbuilds.test.mjs` 有一条回归钉住两句旁白进了日志流（用 `dsh.progress().log` 反查，与用户看到的是同一份数据）。
  - **⚠️ 阶段提示是「猜测」，措辞必须留余地**（`dshMarketPhaseText`）：宿主没有细粒度进度事件，旁白之外的阶段只能凭 `lastCmd` 与输出关键词（`clone` / `prepare` / `reify` 等）粗判，故一律写「正在…」而非「已完成…」。
  - **⚠️ 待确认计划要摆成「单据」，不能只是两行 hint**：原先两行 `hint`（「将安装 `<强>`包名`</强>`（显示名）：」+ 宿主整句 `message` 塞进 `<code>`）；原先「会改哪些文件」没写、确认按钮是 `danger`（红色）排在取消左边；现为 `.mkt-plan` 单据卡：
    - **结构**：`.mkt-plan-head`（动作徽标 `.mkt-plan-badge` + 包名 `.mkt-plan-name` 等宽）/ `.mkt-plan-sub`（显示名 + 版本去向）/ `.mkt-plan-msg`（宿主 `message` 原文）/ `.mkt-plan-effects`（「会改什么」清单）/ 进度区 / `.mkt-plan-actions`（动作行）。左侧竖向色带（`.mkt-plan::before`）随动作变（默认主色，`彻底删除` 走 `--err`），表示「待你点头才动」。
    - **⚠️「会改什么」清单按动作分支写**（分支清单见下条），不能一股脑列全：把「包仍留在磁盘上」写给安装、把「会改写版本范围」写给禁用都是误导，这张单子的价值就在说准。安装支写明改写 `profile/<名>/package.json` 的版本范围 + 连带改 `pnpm-lock.yaml`；`remove` 支写明删依赖 + 连带删包本体；禁用支写明**只往 patch 写 `disabled: true`、包与依赖原样留在磁盘**。三支都写明「动手前自动建快照，失败可回滚」。
    - **⚠️ `.mkt-plan-msg` 要 `white-space: pre-line`**：宿主 `message` 尾部会挂一段 `\n⚠️ 该来源靠 prepare 脚本构建…` 的独立警告，不保留换行会与主句挤成一条线而**被读丢**。
    - **⚠️ 确认按钮从 `danger` 改回 `primary`**：装插件是**常规操作**，整卡标红会让人以为要删东西；真正不可逆的是「彻底删除」。禁用态一并加在「取消」上（原先只有确认有 `:disabled="dshMarketBusy"`，写入期间取消仍可点，点了会清掉 plan 而宿主 pnpm 仍在跑）。
    - **⚠️ 单据必须写出「具体版本号」，不能只说「按目录提供的版本重装」**：用户点确认前想知道的是**落在哪个数字上**；`.mkt-plan-sub` 在 `plan.version` 可得时（安装 / 更新两支，且**非** `exact`）补一句「版本将改为 `vX`」；安装写「将写入版本 `vX`」（全新安装没有「从哪一版来」，写「改为」像覆盖）；`.mkt-plan-effects` 对应 `li` 同时写包名（`npmName`）与目标版本，安装支还带出当前声明范围（`depVersion`）。三处取值由 dryRun 阶段的 `dshMarketPreviewInstall` / `dshMarketPreviewUpdate` 回填（`version` / `npmName` / `depVersion`），拿不到就整句不提，**不写 `v?` 占位**。
    - **⚠️「会改什么」清单必须按动作分支**（`install` / `update` / `remove` / `uninstall` **四支**）：原先 `install` / `remove` / `else` 三支，**`update` 落进 `else`**，而 `else` 写的是禁用说明「只往 patch 写一条 `disabled: true`、包与依赖原样留在磁盘」，用户点「更新」却看到一整段禁用文案。更新单开一支：改写版本范围（`npmName`）：现在 `depVersion`，重装后指 `vX` + 连带改 `pnpm-lock.yaml` + 动手前建快照。**新增动作必须补分支，不要靠 `else` 兜底**：兜底文案只对某一种动作成立。
    - **⚠️ 已装包清单里「目录里没有的包」必须给出说明**（`dshMarketInstalledNote`）：市场目录只渲染目录里有的条目，**已装但目录里没有**的包（自装、作者删了词条、github / tarball 装的）只有「禁用 / 彻底删除」两把钥匙，用户找不到「更新」会以为界面漏了，故直说「目录里没有这个包：没有「更新 / 装这一版」可用，只能禁用或彻底删除」。判据与目录列表**同源**（`dshMarketHitOf` / spec 反查），避免「目录里明明有、这里却说没有」；目录未加载时另给「目录还没加载」，不硬判「没有」。
    - **⚠️ 精确安装（`exact`）的结果卡要画「旧 → 新」**：原文案只显示「已安装 dshmarket @1.65.1」，看不出从哪一版换上来；`marketInstall` 成功返回体补 `from`（`DshMarketInstallResult.from`，**原本只有 update 会给**），取**跑 pnpm 之前**回读的实装版本（`realizedOf`，不是目录版本，目录版本正是滞后的那个）；界面 `install` 分支据此与 `update` 同款措辞（`已安装 X（v旧 → v新）`），拿不到 `from` 才回落原措辞。
  - **⚠️ 卸载入口不能只长在目录条目上，必须有「已装包」清单兜底**（用户实测「卸载按钮看不见找不到」）：原先只有目录条目已装分支一条路径，两类包永远没入口：① **已装但不在目录里**（列表由 catalog 驱动，连行都没有）；② **在目录里但 `install` 字段认不出**（`specKind` 为空，按钮整块不渲染）。「装了什么」的权威真相是 `profile/package.json` + patch，**与目录无关**：宿主 `marketStatus` 的 `installed` 正是二者合并（`installedMap`），早先界面只拿它**匹配目录条目**，从没列出这份表。
    - **修法 ①：卡片新增「已装包」折叠区**（`dshMarketInstalledList` / `dshMarketInstalledFold` / `dshMarketInstalledSummary`），逐行列出 `dshMarketStatus.installed` 的每个键，按「`inDeps` 在前」分组（组内按名字），`inDeps` 决定有没有「彻底删除」，便于看清哪些能真删。每行复用 `dshMarketPreviewUninstall`：**「禁用（留包）」只在 `inPatch` 为真时给**（宿主 `dshPatchToggle` 要求 id 已存在，做不到新加；包不在 patch 里时想禁，得先让它在 patch 里出现，那属于「插件开关」卡的活），**「彻底删除」只在 `inDeps` 为真时给**（不在依赖里时 `pnpm remove` 没东西可删）。
    - **⚠️ 位置必须在「进入市场」之前**：这份清单是**纯本地**的（读 profile/package.json + patch），与联网、目录加载无关。放在 `dshMarketRevealed` 之内等于要求用户先点一次「进入市场」才看得到卸载入口，而多数人根本不进市场，盲区照旧。
    - **修法 ②：放宽目录条目的门禁**，`p.specKind &&` 从已装分支撤掉：卸载走 npm 包名（`marketUninstall` 的 `remove: true` 分支只认 `npm`，spec 反查不到时用 `realDepKey` 按依赖表取回键名），**根本不需要目录 spec**；原判据是把「安装能力」当「卸载能力」。**但「更新」仍需要 specKind**（更新 = 按目录 spec 重装），故单独判 `v-if="p.specKind && dshMarketHasUpdate(p)"`：撤掉外层把关后必须自己判，否则认不出 spec 的条目会摆出点了必报错的「更新」。
  - **⚠️ 彻底删除会顺带清掉 patch 里的残留条目**（对齐上游 dsh-market #799；`patchRowsOf` / `cleanupPatchRows`，`settings.js`）：
    - **为什么必须清**：包删了、patch 条目还在，dsh 每次启动都往 stderr 打 `patch: entry "X" not found`（V2：退出码 0、永不报错，用户完全看不见）；日后重装同名插件还会莫名其妙带着旧 config。
    - **⚠️ 采集必须在 `pnpm remove` 之前**：条目 id 是**用户当初手写进 patch 的名字**（可能是去 scope 的短名），要靠「已装清单 + 包名」反查；包一删，profile/package.json 里的键就没了，反查锚点随之消失。候选 = `oid`（界面 dryRun 算好的 id）∪ `npm` ∪ `shortName(npm, installed)`，**且只保留 patch 里真实存在的 id**（否则「包名恰好等于别的插件 id」会被误删）。
    - **删整段、不区分是否有 config**：`dsh-patch.removeItem` 把该 id 的**所有段**（含 `config:` 子块、同 id 多段）从 `lineIndex` 删到 `endLineIndex`，块间空行与块内注释一并走。与「启用」不同 —— 那时还得保住用户的 config，这里包都没了。
    - **清理失败不回滚、不把整体判失败**：包确实卸掉了，回滚只会让用户把刚删的插件装回来。结论放在返回体的 `patchCleanup: { ok, removed, ids, error? }` 里如实回报，界面念一句「没清干净 + 去哪儿处理」（指向快照回滚 / 手改文件，**不指插件开关卡 —— 那张卡没有删除条目能力**）。
    - 清理走 `removeItem` → `writeFileAtomicSync` → **回读确认一条不剩**（同 E2 / E3 的回读口径）。

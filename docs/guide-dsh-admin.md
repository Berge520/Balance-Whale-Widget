# dsh 以管理员身份启动：备选方案（计划任务免 UAC）

> 这是一份**方案说明**，不是自动化脚本。插件不会创建、修改或删除任何计划任务；
> `public/preload/lib/dsh.js` 里也没有与计划任务相关的调用。是否落地由你在系统层自行决定。
>
> 主路径是设置页的「以管理员身份启动」（`dshElevated`，Windows runas，**每次启动弹一次 UAC**）。
> 本文只讲「不想看到 UAC 时」的备选，以及它的代价。

## 1. 为什么需要备选

Windows 的进程令牌在 `CreateProcess` 时固定，**运行中的进程无法就地提权**。插件因此走的是：

```
结束旧实例 → Start-Process -Verb RunAs 拉起新实例（UAC） → 新实例接管端口
```

「计划任务 + 最高权限」的差别只在于：任务由**任务计划程序服务**用管理员令牌创建进程，
不经过 UAC 确认框 —— 因为「以最高权限运行」这个授权在**创建任务时**就已经一次性给出了。
换句话说，你只是把「每次确认」换成了「事先授权」，并没有消除提权本身。

## 2. 思路

1. **启动器脚本固定路径**：写一个只做一件事的入口（例如 `C:\ProgramData\dsh-elevated\start-dsh.cmd`），
   内容等价于插件现在做的事：`node <dsh>/lib/bin.js web --no-open`。
   路径必须在**管理员可写、普通用户只读**的目录（`C:\ProgramData\...` 而不是 `%TEMP%`、也不是插件安装目录）。
2. **建一个任务**：触发器按需选「登录时」或「按需手动触发」（`/SC ONLOGON` 或 `/SC ONCE` + `/Run` 手动跑）。
3. **安全选项选「使用最高权限运行」**（`/RL HIGHEST`）。这是免 UAC 的唯一开关，也是全部风险所在。
4. 之后由你手动 `schtasks /Run` 或在登录时自动跑；插件的「启动」按钮**不会**触发任务（未实现该集成）。

## 3. `schtasks` 关键参数

| 参数 | 作用 | 本例取值与理由 |
|---|---|---|
| `/TN` | 任务名（删除/查询的钥匙） | 固定名字，例如 `dsh-elevated`；不要用带空格/中文的名字，省得后续转义出错 |
| `/TR` | 要运行的命令 | 指向上面那个**固定路径**的启动器；不要把整条 node 命令塞进来 |
| `/SC` | 触发器 | `ONLOGON`（登录即起）或 `ONCE`（只建一次、之后手动 `/Run`） |
| `/RL` | 运行级别 | **`HIGHEST`**＝最高权限（免 UAC）；`LIMITED`＝普通权限 |
| `/RU` | 以哪个账户运行 | 用**你自己**的账户；用 `SYSTEM` 会丢掉用户环境（映射盘、用户目录、代理设置都看不到） |
| `/RP` | `/RU` 的密码 | 用当前用户时可省略（任务用现有登录会话凭据）；一旦给了密码，密码会进任务存储 |
| `/IT` | 仅在用户登录时运行 | 交互式会话才拿得到用户桌面/网络盘；无人值守场景要另想 |
| `/F` | 同名任务直接覆盖 | 重建时用；**首次创建建议先不带 `/F`**，避免误覆盖别人的同名任务 |

示例（**占位符，不要照抄执行**；`<...>` 全都要换成你自己核对过的值）：

```
schtasks /Create /TN <任务名> /TR "<启动器完整路径>" /SC ONLOGON /RL HIGHEST /RU <你的账户> /IT
```

不要把它包成 `.bat` / `.ps1` 一次跑完 —— 建任务这一步应当是你**逐项确认**后手动执行的动作。

## 4. 创建与验证步骤

1. 建目录并放启动器：目录权限收紧到「管理员完全控制、Users 只读」。
2. 先手动跑一次启动器（普通权限），确认 dsh 能起来、端口与 `--no-open` 行为符合预期；再结束它。
3. 建任务（上表参数），**不要**在任务里加 `cmd /c start` 之类的二次包装，便于排查。
4. 验证：
   - `schtasks /Query /TN <任务名> /V /FO LIST` → 确认「以最高权限运行」为「是」；
   - `schtasks /Run /TN <任务名>` → 起来后在新窗口 `whoami /groups` 查看完整性级别是否 High；
   - 确认**全程无 UAC 弹窗**；
   - 确认 dsh 的 Web UI 仍能被插件探测到（端口可访问、`--no-open` 生效）。
5. 与插件的关系：插件的「结束」按钮对任务起的进程同样会走提权 kill（会弹 UAC）；
   更省事的做法是用 `schtasks /End /TN <任务名>` 结束任务实例，再用 `/Run` 重启。

## 5. 凭证与安全风险（必须先读完）

- **最高权限任务就是一个免 UAC 的提权后门。** 谁能改这个任务（改 `/TR`、改触发器、改运行账户），
  谁就能让系统以管理员身份执行任意代码，而且**不会有任何提示**。默认只有管理员能改任务，
  但「启动器脚本放在用户可写目录」「任务 ACL 被放宽」都会把这个前提打穿。
- **脚本路径必须不可被普通用户改写**：`%TEMP%`、`%APPDATA%`、插件安装目录（uTools 插件目录通常用户可写）
  都不合格。被替换一次就等于永久提权。
- **`/RP` 存密码**：密码会落在任务计划程序的凭据存储里，能读任务定义的人就能拿到；
  能用当前用户会话就不要填 `/RP`。
- **SYSTEM 运行的副作用**：拿不到用户映射的网络盘、用户级代理、用户级 Node 配置（`npm prefix` 等），
  与「以管理员身份启动」遇到的问题同类但更严重。
- **参数漂移**：任务里的命令行一旦写死，之后升级 dsh / 换 Node 路径都不会跟着变；
  建议启动器脚本里做存在性检查并以非零码失败（任务历史里能看到失败原因）。
- **审计缺失**：UAC 弹窗是「人肉审计」。免 UAC 之后，唯一的痕迹是任务计划程序的操作历史
  （默认可能未开启），排查「谁在什么时候提权跑过东西」会明显变难。
- **本插件不做这件事**：插件只负责 runas 主路径；不创建任务、不调用 `schtasks`、不碰系统安全配置。

## 6. 失败与回滚

按顺序执行，任一步失败就停在那里并检查原因（不要连跑）：

1. 先降权：`schtasks /Change /TN <任务名> /RL LIMITED` —— 立刻把「免 UAC」这一条抽掉。
2. 确认降权生效：`schtasks /Query /TN <任务名> /V /FO LIST` 里「以最高权限运行」应为「否」。
3. 结束可能在跑的实例：`schtasks /End /TN <任务名>`；再到设置页点「结束」确认端口已释放。
4. 删除任务：`schtasks /Delete /TN <任务名> /F`，再用 `schtasks /Query /TN <任务名>` 确认「找不到」。
5. 删除启动器目录（或至少确认其中脚本已不再被任何任务引用）。
6. 最后把 dsh 换成普通权限启动：关掉设置页「以管理员身份启动」，重启 dsh 验证一次。

回滚失败时的兜底：任务删不掉（权限/被占用）就先停在步骤 1 的 `LIMITED` 状态 ——
此时它已经不再是提权入口，剩下的只是清理残留。

## 7. 和主路径的对比

| | runas 主路径（插件内置） | 计划任务（本文） |
|---|---|---|
| 每次启动 | 弹一次 UAC | 无弹窗 |
| 结束/重启 | 再弹一次 UAC | `schtasks /End` 无需 UAC |
| 授权时机 | 每次由人确认 | 建任务时一次性授权 |
| 风险面 | 每次都有明确的用户确认 | 长期存在的提权入口，靠 ACL 与目录权限兜底 |
| 维护 | 插件自动跟随 dsh 版本/Node 路径 | 任务命令行写死，升级要手动改 |
| 适合谁 | 偶尔需要管理员插件 | 固定机器、明确接受风险、需要完全无人值守 |

> `--no-open` 请保持默认开启：dsh 若自己去拉浏览器，那个浏览器会继承管理员令牌，
> 结果是拖拽文件失效（UIPI 拦截）且看不到已映射的网络盘。让 Web UI 留在普通权限的浏览器里，
> 只有 dsh 服务端提权，副作用最小。
